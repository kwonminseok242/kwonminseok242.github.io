톡뱅킹: 시각장애인을 위한 음성 뱅킹 앱

말로 송금하는 앱에서, 같은 이체가 두 번 들어와도 한 번만 처리되도록 만들었습니다. AI가 똑똑하게 답하는 것만큼 사고 없이 돌아가는 것이 중요하다고 본 프로젝트입니다.

#LangGraph#FastAPI#PostgreSQL#ReactNative#Idempotency#Accessibility
팀 / 기간6인 팀 · 2026.05 ~ 2026.06 (모의 은행 환경)
내 역할송금 에이전트와 송금 화면(React Native) 개발, 에이전트 구조 공동 결정

서비스 흐름

음성 입력(STT) → LangGraph 멀티 에이전트 → 음성 출력(TTS). 송금은 화자 인증(ASV)을 거친 뒤에만 진행됩니다. 우리FISA 교육 과정의 최종 과제로, 실제 은행 서비스가 아닌 모의 은행 DB 안에서 동작합니다.

판단: 중복 이체를 어디서 막을까

네트워크가 불안정해 앱이 재시도하거나 사용자가 버튼을 연달아 누르면, 서버는 같은 이체를 서로 다른 요청으로 보고 두 번 출금할 수 있습니다.

방법장점단점
서버 메모리·Redis 캐시에 요청 키 저장구현이 빠름서버가 재시작되거나 여러 대면 뚫림
DB에 idempotency_key 컬럼 + UNIQUE 제약 (선택)어느 서버로 요청이 가도 같은 규칙 적용DB 구조부터 바꿔야 함

쉽게 말하면, 같은 이체가 두 번 들어와도 장부 자체에 한 번만 기록되도록 규칙을 걸었습니다.

무엇을 했나

내가 한 일

  • DB에 중복 방지 키 컬럼 추가 (이후 서비스·테스트가 모두 이 키를 전제로 하므로 가장 먼저)
  • 엣지 케이스 2건 발견·수정: 실패한 요청이 정상 응답으로 재사용되는 문제, 동시 연타 시 500 에러가 나는 문제
  • 같은 키로 두 번 요청해도 DB 기록 1건·같은 거래 ID인지 확인하는 테스트 작성
  • 배포 후 이전 수취인·금액이 남는 세션 문제를 로그와 반복 테스트로 발견·추적

팀이 한 일

  • 세션 문제의 원인 확정과 공통 저장소(Redis) 도입 구현
  • Supervisor 도메인 분류·라우팅 등 다른 도메인 에이전트

최종 동작: 완료된 키로 다시 요청하면 기존 영수증 반환, 실패한 키는 409, 동시 요청 충돌도 409로 처리하고 출금 계좌는 잠금(SELECT FOR UPDATE)으로 보호합니다.

함께 정한 화면 방향

발표에서 돋보이도록 화려한 화면을 원하는 팀원들과 방향이 갈렸습니다. 저는 웹 접근성 지침(WCAG 2.1)과 시각장애인 앱 사용성 논문처럼 저시력 사용자를 위한 화면 기준을 정해 둔 자료를 찾아 하나씩 설명했고, 팀은 단순한 화면과 찾은 가이드를 따르기로 정했습니다. 이후 근거 자료를 어떻게 모으고 쓸지 함께 토의하며 진행했습니다.

한계와 배운 점

  • 모의 환경과 테스트로만 검증했고, 실제 운영이나 부하 테스트 결과는 없습니다.
  • 처음 해 본 배포라 서버(worker)가 여러 개일 때의 세션 문제를 미리 예상하지 못했습니다. 다음에는 배포 전에 여러 worker를 띄워 확인할 계획입니다.
